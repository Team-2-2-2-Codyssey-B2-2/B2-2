# 기여 가이드 (CONTRIBUTING)

## 1. 브랜치 전략 (GitHub Flow)

- `main`: 항상 깨지지 않는 상태를 유지합니다. 직접 push는 금지되며(Ruleset `protect-main`), PR과 승인 1명 이상으로만 병합합니다.
- `feature/*`: 작업 1건(이슈 1개)마다 최신 `main`에서 분기하고, PR 병합 후 삭제합니다.

**GitHub Flow를 선택한 이유**
- 3인 팀의 짧은 미션이라 `develop`·`release` 브랜치를 따로 둘 필요가 없습니다.
- 모든 변경이 `feature/*` → PR → 리뷰 → `main` 한 경로로만 들어가서 리뷰와 이슈 추적이 빠지지 않습니다.
- 작업 단위가 작아 오래 갈라진 브랜치가 생기지 않으므로 충돌 범위도 작게 유지됩니다.

## 2. 브랜치 네이밍 규칙

- 형식: `feature/<작업-주제>`, "여러 명이 같은 주제를 나눠 할 때만 <GitHub-ID>- 접두사"
- 영어 소문자와 하이픈(`-`)만 사용합니다(kebab-case).
- 주제는 무엇을 하는 브랜치인지 드러나게 씁니다.

| 예시 | 판정 |
|---|---|
| `feature/string-utils`, `feature/tlswltjq-list-utils` | ✅ |
| `feature/troubleshooting-stash`, `feature/tlswltjq-revert-readme` | ✅ |
| `feature/test`, `feature/work`, `my-branch` | ❌ 주제 불명 / 접두사 없음 |

## 3. 커밋 메시지 및 PR 제목 컨벤션

- 커밋 메시지와 PR 제목은 `<type>: <변경 내용>` 형식을 따릅니다.
- 콜론(`:`) 뒤에는 반드시 공백 한 칸을 넣습니다.
- 변경 내용을 간결하고 명확하게 작성합니다.
- 가능한 경우 무엇을 변경했는지와 왜 변경했는지가 드러나도록 작성합니다.

### 사용 type

| type | 용도 |
|---|---|
| `feat` | 기능(유틸 함수) 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 추가·수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `test` | 테스트·doctest 추가 |
| `chore` | 설정·빌드·.gitignore 등 기타 |

### 작성 예시

**올바른 예시**
- `docs: 프로젝트 디렉토리 구성 및 일부 문서 추가`
- `feat: 사용자 로그인 기능 추가`
- `fix: 잘못된 파일 경로 수정`
- `chore: 불필요한 파일 추적 방지를 위한 gitignore 수정`

**잘못된 예시**
- `docs:프로젝트 디렉토리 구성 및 일부 문서 추가`
- `feat:로그인 기능 추가`

### 의미 없는 커밋 메시지 (금지)

아래 중 하나라도 해당하면 의미 없는 메시지로 보고, 병합 전에 수정합니다.
- 변경 대상을 알 수 없는 단어만 있는 경우: `update`, `fix`, `temp`, `wip`, `final`
- 무엇을/왜 바꿨는지 드러나지 않는 경우: `bug fix`, `edit file`, `Update README.md`
- 수정 방법: push 전이면 `git commit --amend`, 여러 커밋이면 `git rebase -i`(개인 브랜치에서만)

## 4. GitHub Suggestion 커밋 규칙

- PR 리뷰에서 Suggestion을 적용할 때도 동일한 커밋 메시지 컨벤션을 준수합니다.
- GitHub에서 자동 생성하는 `Update .gitignore` 등의 기본 커밋 메시지는 수정합니다.
- 커밋 메시지에는 변경 내용과 목적이 드러나도록 작성합니다.

### 작성 예시

- 변경 전: `Update .gitignore`
- 변경 후: `chore: 불필요한 파일 추적 방지를 위한 gitignore 규칙 수정`

## 5. PR 작성 규칙

### 본문 필수 항목

PR 제목은 3절 커밋 컨벤션(`<type>: <변경 내용>`)을 따르고, 본문에는 아래 4개 항목을 반드시 포함합니다.

```markdown
## 연결 이슈
- Closes #<이슈번호>

## 변경 사항(What)
- 무엇을 추가·수정했는지 (파일/함수 단위)

## 변경 이유(Why)
- 왜 필요한지, 어떤 문제를 해결하는지

## 테스트/검증(How)
- [x] 리뷰어가 그대로 재실행할 수 있는 명령과 결과
      예) `python3 -m doctest src/string_utils.py -v` → 11 passed
```

- **연결 이슈**: 제목이 아니라 **본문**에 `Closes #n`(또는 `Fixes #n`)을 씁니다. `main`에 병합될 때 이슈가 자동으로 닫힙니다. 이슈가 없으면 먼저 만듭니다.
- **How**: "확인함"이 아니라 실행한 명령과 결과를 적습니다. 문서 PR은 렌더링 확인 방법을 적습니다.
- 같은 파일·같은 위치를 수정하는 다른 PR이 있으면 본문에 **충돌 가능성**을 미리 적습니다(7절).

### 작성·병합 규칙

- PR 1개 = 이슈 1개 = 브랜치 1개. 리뷰어가 한 번에 읽을 수 있는 크기로 나눕니다.
- 리뷰어(Reviewers)를 **팀원 최소 1명 이상** 지정합니다.
- 병합 조건
  - 승인(Approve) 1명 이상 (Ruleset `protect-main`이 강제)
  - 충돌 없음, 본문 필수 항목 충족
  - 미해결 Request changes 없음
- 병합 방식은 **Create a merge commit**만 사용합니다. PR 단위 분기·합류가 `git log --graph`에 남아 협업 이력과 리뷰 반영 커밋을 추적할 수 있기 때문입니다(Squash/Rebase 사용 안 함).
- 병합은 원칙적으로 **PR 작성자**가 합니다.

## 6. 코드 리뷰 규칙

### 최소 품질 기준

- 모든 PR에는 **"LGTM/좋아요"가 아닌 실질 코멘트가 1개 이상** 있어야 합니다.
- 실질 코멘트는 **근거**(특정 파일·라인, 실행 결과)를 포함한 아래 중 하나입니다.
  - 질문: 의도·동작이 불분명한 부분
  - 대안 제안: 더 단순하거나 안전한 방법
  - 리스크 지적: 엣지 케이스, 부작용, 규칙 위반
  - 개선 제안: 가독성, 문서화, 일관성
- 의심되는 동작은 **직접 실행해서 재현**하고 결과를 함께 적습니다.

| 구분 | 예시 |
|---|---|
| ❌ | `LGTM`, `좋아요!`, `확인했습니다` (근거·대상 없음) |
| ✅ | `11행: _SEPARATORS에 _가 없어서 to_snake_case("foo_-bar")가 foo__bar가 됩니다. [\s\-_]+로 바꾸면 어떨까요?` (PR #8) |
| ✅ | `39행: 결과를 수정하면 원본 dict도 바뀝니다(재현 코드 첨부). copy.deepcopy를 쓰거나 docstring에 명시해 주세요.` (PR #13) |

### 리뷰 종류

| 종류 | 사용하는 경우 |
|---|---|
| Approve | 필수 항목 충족. 사소한 지적은 "후속 수정 가능"으로 함께 남길 수 있음 |
| Comment | 질문·제안만 있고 병합 여부 판단을 보류할 때 |
| Request changes | 필수 규칙 위반(이슈 미연동, What/Why/How 누락 등) 또는 버그 |

### 리뷰 반영과 상호작용

- 리뷰어와 작성자 사이에 **최소 1회 이상 상호작용**(답글 또는 수정 커밋)이 기록으로 남아야 합니다.
- 반영은 **작성자가 직접** 합니다. 리뷰어가 작성자 브랜치에 대신 push하지 않습니다(리뷰 반영 이력이 작성자 것으로 남도록).
- 한두 줄 수정은 리뷰어가 **suggestion**으로 제안하고, 작성자가 적용할 때 커밋 메시지를 4절 규칙대로 수정합니다.
- 반영 후에는 해당 코멘트에 **답글로 반영 커밋 해시와 검증 결과**를 남깁니다.
  예) `반영했습니다. dc8b769 / doctest 11 passed`
- 반영하지 않기로 했다면 이유를 답글로 남깁니다(예: "문서화로 대신함").

## 7. 충돌 발생 시 대응 흐름

```text
예측·공유 → 해결 → 검증 → 기록 → 확인
```

| 단계 | 누가 | 어떻게 / 어디에 |
|---|---|---|
| 예측·공유 | PR 작성자 | 같은 파일·같은 위치를 수정하는 PR이 있으면 PR 본문에 충돌 가능성 명시. 충돌이 나면 PR 코멘트로 상대에게 알림 |
| 해결 | **나중에 병합되는 PR 작성자** | 최신 `main`을 자기 브랜치에 병합해 해결(아래 명령). 상대 변경의 의도가 불분명하면 지우지 말고 PR 코멘트로 확인 |
| 검증 | 해결한 사람 | 마커가 남지 않았는지, 양쪽 변경이 의도대로 남았는지 확인. 코드 충돌은 doctest 재실행 |
| 기록 | 해결한 사람 | `docs/conflict-resolution.md`에 템플릿대로 기록(참여자·유형·마커 원문·전략·명령·결과·배운 점). 해결 커밋과 같은 PR 또는 바로 다음 PR |
| 확인 | 충돌 상대 | 기록 PR을 리뷰하며 사실관계(원인 커밋, 해결 절차)를 확인 |

기본 해결 명령:

```bash
git switch feature/<내-브랜치>
git fetch origin
git merge origin/main          # CONFLICT 발생
git status -s                  # UU <파일> 확인
# 마커(<<<<<<< ======= >>>>>>>) 정리: keep both / choose one / refactor
git add <파일>
git commit                     # 병합 커밋 생성
python3 -m doctest src/<파일명>.py -v
git push
```

- GitHub 웹 에디터(Resolve conflicts)는 문서처럼 단순한 충돌에만 사용하고, 기록에는 **웹 에디터로 해결했다는 사실**과 로컬 **재현 명령**을 구분해 적습니다.
- 충돌을 피하려고 상대 변경을 합의 없이 지우거나, `main`에 force push하는 것은 금지합니다.
